# 文化祭ブロックチェーン 仕様書・実装まとめ（スマホ運用版）

## 1. システム概要

本システムは、文化祭展示向けに作成する**教育用の簡易ブロックチェーンシステム**です。
**PC1台をサーバーとして起動し、来場者は各自のスマートフォンのブラウザだけで**
アカウント作成・送金・採掘・改ざん体験ができます。アプリのインストールは不要です。

実際の暗号資産で使われる高度な暗号署名・完全なP2P通信・複雑な分散合意アルゴリズムは
実装せず、**取引・ブロック・ハッシュ・チェーン構造・フォーク・最長チェーン採用**という
基本概念が伝わるように簡略化して実装しています。

- 使用技術: **Python 3 / Flask / SQLite / HTML / CSS / JavaScript / SHA-256 / RSA(PyCryptodome) / Pillow**
- 各ノードは独立したSQLiteデータベースを持ち、HTTP通信で他ノードと同期します。

## 2. スマホ運用のための仕組み(今回追加した部分)

先生からの「客のスマホで使えるようWebアプリで完結させ、PCをサーバーにする」という
指示に対応するため、以下を実装しています。

### 2-1. PCをサーバーにする

`app.py` はFlaskの開発サーバーを `host="0.0.0.0"` で起動しており、
最初から**同じWi-Fi(LAN)内の他端末からアクセス可能**です。
起動時にターミナルへ「スマホからのアクセスURL」を自動表示します。

```
============================================================
[起動] ノード名=node1 / ポート=5000
[このPCで開く場合]      http://localhost:5000
[お客さんのスマホから]   http://192.168.11.5:5000
[QRコードで開きたい場合] http://192.168.11.5:5000/qr にPCのブラウザでアクセス
  ※ スマホがこのPCと同じWi-Fi(同じネットワーク)に
    つながっている必要があります。
[管理画面パスワード]     sensei (環境変数 ADMIN_PASSWORD で変更可)
============================================================
```

IPアドレスは `状態.py` の `get_lan_ip()` が自動検出します(インターネット未接続の
会場LANでも動作する方式)。

### 2-2. QRコードでアクセス(`/qr` 画面)

PCの画面(スクリーン投影 or 印刷)に `http://<PCのIP>:ポート/qr` を表示すると、
アクセス用URLのQRコードが表示されます。お客さんはスマホのカメラで読み取るだけで
このシステムを開けます。QRコード画像はPillowのみで自前生成しており
(`表示/qr生成.py`)、外部のQRコード生成サービスへの通信は発生しません
(会場のWi-Fiがインターネットに繋がっていなくても動作します)。

### 2-3. 「マイページ」方式(スマホごとに自分のアカウントを記憶)

- アカウント作成時、そのスマホのブラウザ(セッションCookie)に「自分のアカウント」
  として自動的に記憶されます。
- 以後、送金・採掘の画面では**ドロップダウンで自分の口座を選ぶ必要がなく**、
  常に自分のアカウントが送金者/採掘者として使われます。これにより、
  他人のアカウントから勝手に送金するといった誤操作・なりすましを防いでいます。
- `/me` (マイページ)で、自分の残高・公開鍵、送金/採掘へのショートカットを確認できます。
- 端末を共有する場合(展示スタッフ機など)は、マイページの「記憶を解除する」で
  そのスマホの記憶だけをリセットできます(アカウント自体は消えません)。

### 2-4. 管理画面のパスワード保護

QRコードで誰でもトップページに来られる運用になったため、`/admin`
(改ざん実験・全データ初期化)は簡易パスワードで保護しています。
デフォルトのパスワードは `sensei` です。変更する場合は環境変数で指定してください。

```bash
ADMIN_PASSWORD=好きな文字列 python app.py
```

これは本格的な認証ではなく、あくまで「生徒が誤って/悪戯で管理機能に触れない」
ための簡易的なゲートです。

### 2-5. 複数人が同時にアクセスしても大丈夫か

`app.run(..., threaded=True)` にしてあるため、複数のスマホから同時に
アクセスされても他の人の操作をブロックしません。また `debug=False` を
デフォルトにしており(お客さん向けの画面でエラーデバッガが露出する事故を防止)、
開発時だけ `DEBUG=true` を指定して詳細エラーを見られるようにしています。

### 2-6. ユーザー名+パスワードでのログイン(今回追加した部分)

アカウントの乗っ取り・なりすましを防ぐため、アカウントごとにパスワードを設定し、
「ユーザー名+パスワード」でのログイン制に対応した。

- アカウント作成: `/account` で「ユーザー名+パスワード(+確認用)」を入力。
  作成直後は自動的にログイン状態になる(会場での体験を止めないため)。
- ログイン: `/login` でユーザー名+パスワードを入力してログイン。
  2回目以降のアクセス、ログアウト後、別端末からのアクセスはこちらを使う。
- パスワードは平文のまま保存せず、**PBKDF2-HMAC-SHA256(ランダムsalt付き、
  10万回ストレッチ)** でハッシュ化して保存する(暗号/パスワード.py)。
  hashlib / secrets は標準ライブラリなので依存パッケージは増えていない。
- ユーザー名はシステム内で一意(重複不可)。これにより
  「ユーザー名+パスワード」で本人を一意に特定できる。
- 未ログインで送金・採掘・マイページにアクセスすると `/login` へ誘導される。
- ログイン試行時、ユーザー名の存在有無とパスワード誤りの区別を
  画面上では出さない(アカウント存在の推測を難しくする一般的な配慮)。
- パスワードの最低文字数は 画面/アカウント画面.py の `PASSWORD_MIN_LENGTH`(既定4)。
- 注意: パスワード制導入前に作られた旧DBのアカウントはパスワード未設定のため
  ログインできない。その場合は `/admin` の全初期化(展示開始時の想定動作)か、
  新規アカウントの作成を案内すること。

### 2-7. QRコードでの受け取り・送金(今回追加した部分)

スマホ同士でアドレス(公開鍵)を手入力させずに送金できるようにする機能。

- **受け取り用QR**: ログイン後のマイページ(`/me`)に、自分を受取人にした
  送金URLのQRコードを表示する。画像は `/my-qr.png` で生成する。
- **QRの中身**: `http://<サーバーのLAN IP>:<PORT>/send?user=<ユーザー名>`
  というURL。友だちがスマホの**標準カメラ**で読み取ると、そのURLの
  送金画面が開き、受取人が選択された状態で表示される。
- **金額固定QR(売店向け)**: マイページで金額を指定すると
  `.../send?user=<ユーザー名>&amount=<金額>` のQRに切り替わる。
  例: 売店のQRを読めば「受取人=売店 / 金額=300」まで入力済みで開く。
- **QRが小さくなる工夫**: 公開鍵(数百文字)ではなく**一意なユーザー名**を
  URLに使うことでQRを小さく保ち、暗い会場でも読み取りやすくした。
  ユーザー名は日本語でもOK(URL内ではpercent-encodingされる)。
- **署名は省略しない**: QRで自動入力されるのは受取人と金額だけ。
  送金ボタンを押すと、これまで通り**送信者の秘密鍵で電子署名**されてから
  検証・未承認取引として保存される。「なりすまし送金は署名で防がれる」
  という教育的ポイントをQRでも崩さない。
- **エラー時の案内**: 自分自身のQRを読んだ場合・存在しないユーザーのQRを
  読んだ場合は、送金画面の上部にその旨を表示する(送金は実行されない)。
- **生成方式**: 追加パッケージなし。既存の表示/qr生成.py(自前実装の
  QRコードジェネレータ+Pillow)を流用する。
- **ブラウザ内カメラスキャンは採用していない理由**: カメラAPI
  (getUserMedia)はHTTPSが必須のため、HTTPの学内LAN運用では動かない。
  そこで「標準カメラで読む→URLが開く」方式にしている(自己署名証明書や
  HTTPS化の運用負荷を避ける判断)。

### 2-8. 管理者ウォレットと初期配布(今回追加した部分)

「運営が最初にコインを持っていて、来場者はそれを送金・採掘で流通させる」
という展示シナリオを実現するため、管理者ウォレットを自動で用意する。

- **自動作成**: サーバー起動時と `/admin` の全初期化の直後に、
  アカウント/初期配布.py の `ensure_admin_wallet()` が動く。
  管理者ユーザー名(デフォルト: `admin`)のアカウントが無ければ作成する。
- **初期配布の実現方法**: 残高テーブルへの直接書き込みは**行わない**
  (残高は必ずチェーン走査から計算するという設計ルールを守るため)。
  代わりに `SYSTEM -> 管理者` の**発行取引(INITIAL_SUPPLYコイン)**を
  採掘報酬と同じ仕組み(送信者SYSTEM=署名不要・残高チェック対象外)で
  作成し、起動時に1ブロックとして採掘してチェーンに記録する。
  ビットコインのコインベース(最初の1枚はどこから来るか)の教材になる。
- **採掘.py の変更**: `mine()` に `include_reward=False` を追加。
  初期配布ブロックには採掘報酬を含めない(管理者の残高がちょうど
  1,000,000になる。通常採掘は従来どおり報酬付き)。
- **二重発行の防止**: 管理者名のアカウントが既に存在する場合は何もしない。
  発行取引は「アカウントを新規作成した時だけ」記録する。
- **全初期化との連動**: `/admin` のリセットでチェーン・アカウントが
  消えても、直後に管理者と1,000,000コインが自動で復活する
  (朝リセット→翌日も営業、がサーバー再起動なしで回る)。
- **設定(環境変数)**: `ADMIN_WALLET_NAME`(既定`admin`) /
  `ADMIN_WALLET_PASSWORD`(既定`kinka`) / `ADMIN_INITIAL_SUPPLY`(既定`1000000`)。
  起動時のターミナルに管理者のユーザー名・パスワードを表示する。
- **複数ノード運用の注意**: 各ノードがそれぞれ発行ブロックを作ると
  チェーンが分岐する。副ノード側は `ADMIN_INITIAL_SUPPLY=0` を指定する
  (発行なし・アカウント作成のみ行う)。

## 3. 実装した設計ルール(原仕様書より)

| ルール | 実装箇所 |
|---|---|
| 各ブロックは前ブロックのハッシュ値を保持し、鎖状に接続する | `ブロックチェーン/ブロック.py`, `暗号/ハッシュ.py` |
| 過去データを書き換えると後続ブロックとの整合性が崩れ改ざんを検知できる | `ブロックチェーン/検証器.py`, `表示/改ざん表示.py` |
| ノードは公開鍵をアカウントとして扱い、送金時に秘密鍵で電子署名する | `暗号/鍵管理.py`, `暗号/電子署名.py`, `ブロックチェーン/取引.py` |
| 受信ノードは公開鍵で署名検証し、正しい場合のみ本人による送金として認証する | `ブロックチェーン/取引.py: verify_transaction()` |
| 送金データは未承認取引として一時保存され、採掘でブロック化される | `ブロックチェーン/ブロックチェーン.py` |
| 残高はチェーンを先頭から遡って計算する | `ブロックチェーン/残高計算.py` |
| 新しいブロックはブロードキャストで送られる | `通信/ブロードキャスト.py` |
| ハッシュ関数の計算に成功した者に報酬を与える(Proof of Work) | `ブロックチェーン/採掘.py`(報酬10コイン) |
| フォーク発生時は最も長いチェーンを正統チェーンとして採用する | `ブロックチェーン/フォーク管理.py` |
| 新ノード参加時、他ノードのチェーンと比較し長ければ切り替える | `ブロックチェーン/チェーン同期.py` |
| 「受信時は必ず検証」「追加前も必ず検証」「同期時はチェーン丸ごと検証」 | `ブロックチェーン/検証器.py` を全ての受信・追加・同期経路で呼び出し |
| ノードは公開鍵をアカウントとして扱い、ログインはユーザー名+パスワードで行う | `画面/アカウント画面.py` (`/login`), `暗号/パスワード.py`, `データベース/アカウント保存.py` |
| ブロックチェーンの値をあえて弄れるようにする(改ざん体験) | `画面/管理画面.py`, `表示/改ざん表示.py` (パスワード保護された管理画面から実行) |
| ゲーム終了時にコインを運営に返させる | `画面/管理画面.py: admin_reset()` (チェーン・アカウントを全初期化) |

## 5. セットアップ・起動方法

```bash
cd 文化祭ブロックチェーン
pip install -r requirements.txt   # Flask / pycryptodome / requests / Pillow
python app.py
```

起動すると、ターミナルに「PC自身で開く用のURL」と「スマホから開く用のURL」が
両方表示されます。

### 当日の実際の流れ(例)

1. 会場で先生用PCとお客さん全員のスマホを**同じWi-Fi**に接続する。
2. PCで `python app.py` を実行する。
3. PCのブラウザで `http://localhost:5000/qr` を開き、QRコードをスクリーンに映す
   (または印刷して受付に貼る)。
4. お客さんは各自のスマホでQRコードを読み取るだけでアクセス完了。
   URLを手入力する必要はない。
5. 各自 `/account` でアカウントを作る → 自動的に「マイページ」が自分専用になる。
6. `/mine` で採掘 → 自分の残高に報酬が入る。`/send` で友達に送金。
7. `/admin` で(パスワード入力後)改ざん実験や、展示終了時の全体リセットを行う。

### 複数PCをノードとして同期・フォークを見せたい場合

```bash
NODE_NAME=node1 PORT=5000 python app.py
NODE_NAME=node2 PORT=5001 python app.py
```

それぞれの「ノード」画面から相手のURL(例: `http://192.168.1.10:5001`)を登録し、
「全ノードと同期する」を実行すると、より長いチェーンへ切り替わる様子を確認できます。

## 6. 画面構成

| URL | 画面 | 内容 |
|---|---|---|
| `/` | チェーン全体 | ジェネシスブロックから最新ブロックまでを鎖状に可視化 |
| `/account` | アカウント一覧・新規作成 | ユーザー名+パスワードで作成。作成すると自動ログイン | 
| `/login` | ログイン | ユーザー名+パスワードでログイン。未ログイン時の各画面はここに誘導される |
| `/me` | マイページ | 自分の残高・公開鍵、送金/採掘へのショートカット、ログアウト |
| `/send` | 送金 | 受取者・金額を指定(送金者は常に自分)。署名して未承認取引に |
| `/mine` | 採掘 | ボタン一つでProof of Work実行(採掘者は常に自分。報酬10コイン) |
| `/explorer` | エクスプローラー | ブロック番号/アドレス/ハッシュでチェーン内を検索 |
| `/fork` | フォーク | 採用されなかった孤立チェーンと分岐点を可視化 |
| `/nodes` | ノード | 他ノードの登録・同期実行 |
| `/qr` | QRコード | アクセス用URLをQRコードで表示(スクリーン投影・印刷用) |
| `/admin` | 管理(要パスワード) | ブロックの値を直接書き換える改ざん実験、全データ初期化 |

### ノード間API(JSON, サーバー同士の通信用)

| メソッド | パス | 内容 |
|---|---|---|
| GET | `/chain` | 自ノードの現在のチェーンを返す |
| POST | `/blocks/receive` | 他ノードから新ブロックを受信(検証してから追加) |
| POST | `/transactions/receive` | 他ノードから新取引を受信(検証してから未承認取引に追加) |
| GET | `/nodes/resolve` | 登録済み全ノードとチェーンを比較し最長を採用 |

## 7. 教育的なポイント(展示での見せ方の例)

1. **改ざん検知の体験**: `/admin` でブロック内の取引金額を書き換えると、ハッシュ値は
   再計算されないため、そのブロックの「自身のハッシュ」と、次ブロックが持つ
   「前ブロックのハッシュ」が食い違い、以降のブロックすべてが「不一致」と表示されます。
2. **フォークと最長チェーン採用**: 複数PCを同時に動かし、ほぼ同時に採掘を行うと
   チェーンが分岐します。`/nodes` の同期実行や `/fork` 画面で、
   「より長いチェーンが正統として採用され、短い方は孤立ブロックとして残る」
   様子を見せられます。
3. **残高はチェーンの積み重ねで決まる**: 残高は特定の変数に保存されているのではなく、
   `ブロックチェーン/残高計算.py` が毎回チェーン全体を先頭から走査して計算しています。
4. **展示終了時のリセット**: `/admin` の「全て初期化」で、その日発行された全コイン・
   アカウント・チェーンを消去し、次の回の来場者に向けてジェネシスブロックのみの
   状態に戻せます。

## 8. 注意事項・既知の制約(教育目的の簡略化)

- 秘密鍵はサーバー側のSQLiteに保存しています。来場者がブラウザだけで送金体験
  できるようにするための割り切りであり、実運用の暗号資産のようにクライアント側で
  秘密鍵を管理する設計にはしていません。
- Proof of Workの難易度(`ブロックチェーン/採掘.py` の `DEFAULT_DIFFICULTY`、
  デフォルト4)は展示会場でテンポよく体験できるよう軽めに設定しています。
- ノード間通信は素朴なHTTP(JSON)で行っており、実際のP2Pネットワークにあるような
  ピア探索やNAT越えの仕組みはありません。**同一LAN内での利用を想定**しています。
- スマホからアクセスできない場合、`/qr` 画面下部にトラブルシューティング
  (Wi-Fi接続確認、モバイル通信オフ推奨、会場Wi-Fiの端末間通信制限、
  ファイアウォールのポート開放)を掲載しています。
- `python app.py` はデフォルトで `debug=False` で起動します(お客さん向けの
  公開環境でエラー画面から任意コード実行ができてしまう事故を防ぐため)。
  開発中に詳細なエラーを見たい場合のみ `DEBUG=true python app.py` としてください。
- `pip install` にはインターネット接続が必要です。開発・動作確認を行った
  サンドボックス環境ではネットワークが遮断されていたため、`Crypto`(PyCryptodome)
  互換の簡易シムを使ってテストしましたが、アカウント作成→マイページ→採掘→
  送金→残高反映→改ざん検知→パスワード保護された管理画面→リセット、
  および自前QRコード生成(OpenCVによるデコード確認込み)まで、
  一連の流れは動作確認済みです。実際に配布する際は、通常のインターネット環境で
  `pip install -r requirements.txt` を行った上でご利用ください。

## 9. 元の仕様書ファイルとの対応

このZIPには、いただいた元の仕様書2ファイル(システム仕様・ディレクトリ構成メモ)の
内容をもとに実装したコード一式が含まれています。各Pythonファイルの冒頭コメントに、
元の仕様書に書かれていた要件(関数名・キー名・実装方針など)をできるだけそのまま
反映しています。スマホ運用のために追加した機能(マイページ・QRコード・管理者
パスワード・LAN IP自動検出など)についても、各ファイルの冒頭コメントに理由を記載しています。
